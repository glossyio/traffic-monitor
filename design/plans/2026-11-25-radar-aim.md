# The radar's aim: a speed correction from how the unit is mounted, recorded with time

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin enters how far the radar points across the road, the control app works out a speed correction for each direction and sends it to the radar when the form is saved, the device records what the radar reports with the time it took effect, and a view that takes in an intersection is ticked, recorded, and matched to speeds by a stricter rule.

**Architecture:**
- The radar applies the correction, as it can today. What changes is who sets it and what is recorded. Two typed keys under the radar in `config.yml` hold the two angles, Node-RED sends them after every other setup command, and a `^/` command in the extra commands is never sent. So the form's angles are what the radar ends with.
- What the radar answers is the record. After every setup Node-RED already asks the radar for its settings. A third setup-history table, `setup_radar`, keeps eight of those answers with `started` and `ended`, and `events_with_setup` shows the row in force beside each event. A reader who wants the raw speed multiplies by the cosine of the angle in force.
- The angle into the road is a mounting fact, beside the five: it lives in the control app's store, in the radar's `deployment:` block, and on the radar's deployment row, and a change of it is a move or a better measurement, as the admin answers. The street's facts and the intersection tick describe the street, so they are corrected in place and ask nothing.
- Every rule is in Python with no I/O: the limits and the question in `mounting.py`, the road geometry in a new `aim.py`. The page sends a dry run as the admin types and draws what the API answers.
- Four pull requests, each stacked on the one before. PR 1 changes how the radar is set up and records it, and changes nothing that is measured. PR 2 puts the aim on the record and adds the intersection rule. PR 3 is the API. PR 4 is the form.

**Tech Stack:** Node-RED 5.0.10 function nodes (JavaScript in `flows.json`), SQLite migrations run by `tmdb_migrate.py`, Ansible and Jinja for the installer, Python 3.11+ (FastAPI, pydantic 2, ruamel.yaml; no new dependency), Vue 3 + Vuetify 3 + TypeScript (Vitest, jsdom; no new package), pytest with the function-node harness in `script/tests/test_node_red_flows.py`, the device tests in `script/devpi/tests`, Material for MkDocs.

**Decisions.** The maintainer's are marked with a date. The rest are calls made while writing this, open to change.

1. **Four pull requests, and the extra commands apart (maintainer, 2026-11-25).** Boxes for the radar's minimum speed and magnitude and the list of extra commands get their own plan, under the same series name. This plan records the two values and shows them read-only.
2. **A move records none of the radar's values, at a place used before as at a new one (maintainer, 2026-11-25).** Deploy here removes the angle into the road, the street's facts, the tick, and the two cosine keys from `config.yml`, so the radar is sent 0 and that 0 is recorded. At a place used before, the values last saved there are offered as "From last time", and a save confirms them. It is the rule the height and tilt already follow. A wrong angle recorded as measured costs more than a correction that waits: 5° off is about 3% of the speed at 20° and 9% at 45°.
   - It follows that a correction someone typed into `config.yml` by hand is dropped at the first move, as an angle the form saved is.
3. **The installer switches off the serial nodes of radar ports that aren't there (maintainer, 2026-11-25).** The serial node logs one error for each missing port at every start and tries the port again every 15 seconds, and no value of the port setting makes it skip one. The installer already knows which ports exist.
4. **The beam is 20° across the road and 24° up and down (maintainer, 2026-11-25),** the maker's half-power figures for the OPS243's antenna in today's housing.
5. **What the form asks (maintainer, 2026-11-17).** The angle into the road is the one fact a correction needs, with the height and tilt the radar already has. The street's facts are optional, recorded when entered, and the form says both things plainly. The correction is applied in the radar as soon as the form is saved, with the effect stated before the save. The usual mounts fill in an angle. The intersection tick is recorded, changes the matching rule, and puts zone advice on the Cameras page and in the setup guide.
6. **Names.** The unit is in the name, as in the five.
   - Under a radar in `config.yml`: `cosine_inbound_deg`, `cosine_outbound_deg`. The first draft said `cosine_inbound` and `cosine_outbound`; with `_deg`, nobody types the cosine itself.
   - In a sensor's `deployment:` block, on `deployment` rows, in the store, and in the API: `road_angle_deg`, `lane_distance_m`, `lane_width_m`, `lanes_toward`, `lanes_away`, `turn_lane`, `toward_side`, `intersection`.
   - `setup_radar`: `id`, `started`, `ended`, `radar`, then `part_number`, `firmware_version`, `cosine_inbound_deg`, `cosine_outbound_deg`, `speed_unit`, `sampling_rate`, `speed_min`, `magnitude_min`. The first four line up with `setup_camera`'s. None is a setting from `config.yml`, so none has a `config_` prefix: each is what the radar answered.
7. **Toward and away.** "Toward the unit" is the radar's inbound (`^/+`), and "away" is its outbound (`^/-`), the words the flows already use for `direction_calc`.
8. **A `^/` command in the extra commands is never sent, and the two keys are the only source of the angles.** Node-RED's start converts an old file (`tm-control migrate --node-red-cosine`, beside the heading's line): a `^/` entry beside a blank key moves into the key, a pair of zeros is dropped, and an entry beside a key that is set is removed. Until it is converted, an entry is reported as a config error by its key's path and the radar is sent the key's value, which is 0 when blank. The conversion runs at Node-RED's start, not in the installer's pass, so a file put back from an old backup is converted too.
9. **`opt_api_commands_array` stays a JSON list in a string.** Its default becomes `'[]'`. Turning it into a YAML list belongs to the next plan of this series.
10. **The engine starts a deployment when `road_angle_deg` changes, and never for the street's facts or the tick.** Those seven are written into the open row in place whenever they differ from `config.yml`, as the place's time zone is. So a hand edit of the angle is a move, like a hand edit of the height, and a hand edit of a lane count is a correction.
11. **The angle joins the question.** A changed or cleared `road_angle_deg` counts for "Did the unit move or turn?", with "moved or turned" chosen in advance at 10° or more. Filling it in for the first time doesn't count. The street's facts, the tick, and typed angles never count and are never listed.
12. **Under either answer the radar's correction changes from the save on.** "Measured it better" corrects the deployment row's angle in place; the speeds recorded before the save keep the correction they were measured with, and `setup_radar` says which. Nothing recomputes a stored speed.
13. **The angles can be typed.** The radar's section has "Worked out from the angle" (the default) or "I'll type the angles". Typed angles are stored for the place as the form's own (`cosine_typed`), so a reset of `config.yml` gets them back.
14. **The street's facts are used only when they make a street:** a distance, a width, and at least one lane. Otherwise both directions get the angle into the road, and the form says which fact is missing for the drawing. They are saved as entered either way.
15. **A radar that hasn't said which model it is gets the shorter range,** 60 m, and the form says so. The first draft had the form ask.
16. **No field for the cross street.** Nothing sent to the radar depends on it.
17. **The tick belongs to the radar and to each camera that names it.** The API copies a radar's tick to those cameras. A camera with no radar has a tick of its own. An air-quality monitor has none.
18. **`intersection` and `turn_lane` are stored as 1 or empty,** never 0: a tick box can't tell "no" from "nobody said".
19. **An event the intersection rule leaves without a radar speed gets `direction_source` `zones_intersection`** when the zones gave it a direction. No new column, and no change to an event with no direction.
20. **The radar's answers that are recorded:** the eight columns of Decision 6. The serial number is never read into the table, the status answer, or the upload's setup rows. The `radarinfo` attribute, which already carries everything the radar answers, is unchanged.
21. **A round of answers that doesn't hold the radar's part number changes nothing:** no row is closed, and the status keeps the answers from before with their time.
22. **The form warns from what the radar reports, not from a table of firmware versions.** When the answers hold no angles, it says the radar didn't report them and that its firmware may predate the correction (1.1.6 on an OPS243-A, 1.2.0 on an OPS243-C, from the maker's API note).
23. **After a save that changed the angles, the API waits up to 20 seconds for the radar's new answer,** as a deploy waits for its rows. Without one, the page says the radar hasn't confirmed yet and offers **Check again**.
24. **One SVG for the intersection picture, kept as two identical files** (`docs/assets/images/intersection-zones.svg` and `tm-control/ui/src/modules/cameras/intersection-zones.svg`), because the UI's sources reach the device as an archive of its own folder. A test compares them.
25. **In fake mode a made-up OPS243-A answers three seconds after `config.yml` changes,** with the angles the file holds, so the read-back and "hasn't confirmed yet" can both be seen on a laptop.

## What it must do

1. **Two typed keys for the correction.** Under `sensors.radars.<name>` in `config.yml`:

   | Key | Meaning | Values |
   |---|---|---|
   | `cosine_inbound_deg` | the angle between the beam and traffic coming toward the unit | 0 to 89, one decimal; blank is 0 |
   | `cosine_outbound_deg` | the same for traffic going away | 0 to 89, one decimal; blank is 0 |

   A value outside that (a number in quotes, a negative, 90) is 0 with a config error that names the key's path and no value.
2. **The order of the radar's setup.** `PI`, the clock, the time zone, the Traffic Monitor's own commands, the extra commands, then `^/+<inbound>` and `^/-<outbound>` (each with one decimal and a line ending), then `PA` and `A!`. A string in `opt_api_commands_array` that starts with `^/` after trimming is never sent, and is a config error by its key's path. A value of `opt_api_commands_array` that isn't a JSON list of strings gives no extra commands and a config error. Its default is `'[]'`.
3. **An old file keeps its correction.** Node-RED's start converts it before any flow runs: for each radar, a `^/+n` or `^/-n` entry (n from 0 to 89) moves into its blank key, unless n is 0, and is removed from the list; an entry beside a key that is set is removed; an entry that doesn't parse is left, with a warning by key path. The file is saved once, with a backup, only when something changed.
4. **What the radar answers is recorded with time.** `setup_radar` holds, for each radar in `config.yml`, rows of:

   | Column | From the radar's answer | Type |
   |---|---|---|
   | `part_number` | `Product` | TEXT |
   | `firmware_version` | `Version` | TEXT |
   | `cosine_inbound_deg` | `InboundSensorAngleDegrees` | REAL |
   | `cosine_outbound_deg` | `OutboundSensorAngleDegrees` | REAL |
   | `speed_unit` | `Units` | TEXT |
   | `sampling_rate` | `SamplingRate` | INTEGER |
   | `speed_min` | `RequiredMinSpeed`, in `speed_unit` | REAL |
   | `magnitude_min` | `MagnitudeMin` | REAL |

   with `id`, `started`, `ended` (Unix milliseconds), and `radar` (the key under `sensors.radars`). A row is closed and a new one started only when an answer differs. An answer the radar didn't give is empty. A radar that `config.yml` no longer lists has its row ended. A round with no part number changes nothing.
5. **`events_with_setup` gains the radar's columns** for the radar in the event's `radarName`: `setup_radar_id`, and each of the eight as `radar_<column>`. An event with no radar, or no row in force, has them empty.
6. **Node-RED's status carries the answers.** In `GET /tm-internal/status`, each radar gains `info`: `null`, or the eight with `answered_at`.
7. **The setup rows upload** with **Share data**, as the device's and the cameras' do: telemetry `setup` gains `radars`, cut to a new `setup_radar` list in `upload-lists.json`.
8. **No serial port is opened for a radar that isn't there.** The installer writes the device's `flows.json` with the serial nodes of each radar whose port didn't exist when it ran switched off. The repo's `flows.json` has none switched off.
9. **Eight facts on the deployment row.**

   | Fact | Name | Values | Stored as | On |
   |---|---|---|---|---|
   | Angle into the road: 0 is straight along it, 90 straight across | `road_angle_deg` | 0 to 89 | REAL, one decimal | radars |
   | Straight across to the near edge of the first lane that carries traffic | `lane_distance_m` | 0 to 100 | REAL, two decimals | radars |
   | Width of one lane | `lane_width_m` | above 0, at most 10 | REAL, two decimals | radars |
   | Lanes coming toward the unit | `lanes_toward` | 0 to 3 | INTEGER | radars |
   | Lanes going away | `lanes_away` | 0 to 3 | INTEGER | radars |
   | A turning lane in the middle | `turn_lane` | ticked | INTEGER, 1 or empty | radars |
   | The side traffic toward the unit is on | `toward_side` | `near`, `far` | TEXT | radars |
   | This view takes in an intersection | `intersection` | ticked | INTEGER, 1 or empty | radars and cameras |

   Each is optional and empty by default, and is read from the sensor's `deployment:` block as the five are. A radar's key found on another kind of sensor is ignored.
10. **A deployment starts when the place, any of the five, or `road_angle_deg` changes** in `config.yml`. The other seven never start one: an open row that differs from the file is rewritten with the file's.
11. **At an intersection, a speed needs the radar's zone and a matching direction.** For an event of a camera whose `intersection` is ticked: a radar speed is attached only when the event entered `zone_radar` and the zones' direction is one the radar saw. An event that didn't enter `zone_radar` gets no radar reading, and `direction_source` `zones_intersection` when the zones gave it a direction. No direction or speed is taken from the radar alone. Frigate's own speed still fills `speed_calc` where the radar gave none. Unticked, nothing changes.
12. **The correction is worked out from the mount.** With the radar's height `H`, its tilt `P`, the angle into the road `A`, and the radar's range (100 m for an OPS243-A, 60 m for an OPS243-C or a radar that hasn't said):
    - Coordinates: the unit at the origin, `x` along the road the way the radar is aimed, `y` across the road toward the lanes, `z` up. The beam's axis is `b = (cos P cos A, cos P sin A, -sin P)`, its across axis `c = (-sin A, cos A, 0)`, and its up axis `u = b × c`.
    - A spot `p` is in the beam when `p·b > 0`, it is within the range, and `(atan2(p·c, p·b) / 10°)² + (atan2(p·u, p·b) / 12°)² ≤ 1`. That sum is the spot's *nearness*.
    - A lane's centre line is tested 0.6 m above the road, where a car reflects: spots `(s, y, 0.6 - H)` for `s` = 0, 0.05, 0.10, ... m up to the range, `y` the lane's centre. The lane's *stretch* runs from the first spot in the beam to the last, and its angle is `acos(s / |p|)` at the middle of the stretch.
    - Lanes run across the road from the unit: the near side's lanes, the turning lane, the far side's. The first lane's centre is `lane_distance_m + lane_width_m / 2`, and each next one is a width further. A turning lane takes its width and is never tested.
    - A direction's angle is the mean of its lanes' angles, to one decimal. A lane with no spot in the beam is *outside*: it gives the angle at its spot of least nearness, and is counted only when every lane of its direction is outside. A direction with no lanes, and both directions when the street's facts don't make a street (Decision 14) or the radar has no height or tilt, get `A`.
    - Typed angles take the place of the worked-out ones. With no angle into the road and none typed, both are 0.
13. **What the form is told beside the angles,** all worked out by the API:
    - for each direction: how low the radar reads without the correction, `(1 - cos a) × 100`; how much the correction raises its speeds, `(1 / cos a - 1) × 100`; the shortest stretch among its lanes, and the seconds a vehicle at 30 mph (13.4112 m/s) spends in it;
    - for each lane: its stretch, and what the direction's correction leaves over in it, `(cos a_lane / cos a_direction - 1) × 100`;
    - what a save does to speeds, against the keys `config.yml` holds now: `(cos a_now / cos a_new - 1) × 100` for each direction;
    - what 5° of error in the aim costs, `tan A × 5° in radians × 100`, to a whole percent (3 at 20°, 9 at 45°);
    - above 35°, that the aim is steep, with how far the readings of one pass differ, `(cos(A - 10°) / cos(A + 10°) - 1) × 100` (14 at 20°, 43 at 45°);
    - when a lane is outside the beam: the largest whole angle at or below `A` that brings every lane in, and the smallest distance to the nearest lane, in steps of 0.25 m up to 30 m, that does;
    - what a vehicle on a cross street reads as a share of its true speed, `tan A × 100` (36 at 20°, 100 at 45°).
14. **The angle into the road is a mounting fact.** It is saved with the five, corrected in place or started as a new deployment by the answer to "Did the unit move or turn?" (Decision 11), written to the radar's `deployment:` block, and stored for the place. The street's facts and the tick are written to the file and the store, and the engine corrects the open row.
15. **A save writes the two cosine keys** for every radar it writes, in the same save of `config.yml` as the mounting. A save that changes neither the mounting nor the keys writes nothing.
16. **What the radar reports back is shown.** The API answers, for each radar, the eight with their time, and whether the angles in force differ from the file's by more than 0.05°. After a save that changed the keys it waits up to 20 seconds for an answer newer than the save.
17. **A move records none of it** (Decision 2), and a reset of `config.yml` gets back what was saved and confirmed for the place in use: the angle, the street's facts, the tick, and the two keys, in the same save as the place's id.
18. **Usual mounts fill in an angle.**

    | Key | Angle into the road | Intersection |
    |---|---|---|
    | `tripod` | 45° | |
    | `pole` | 30° | |
    | `window` | none | ticked |

19. **The form (PR 4):** in each radar's section of the Mounting page, the angle into the road, the street's facts (optional, and said to be), the road from above with each lane and its stretch, a line for each direction, the notes for a steep aim and a lane outside the beam, the choice to type the angles, the sentence that says what saving does to speeds, what the radar reports back, and the intersection tick with its note. It works on the hotspot.
20. **The Cameras page shows the zone advice** under a camera's zones while that camera's view is ticked as an intersection, with the picture opened in place. The setup guide's zones step has the same advice and picture, always.
21. **Upload.** The eight facts are sent on deployment rows because the `deployment` list names them. The notice says so.
22. **Nothing here identifies a place or a person.** The values hold no coordinate, name, or description, so they may be in an audit row and uploaded. The radar's serial number is not among them.
23. **Docs** say what is recorded, how to measure it, and what a change does, in the same PR as the code they describe.

## Global Constraints

- **The names, limits, and arithmetic are those in "What it must do", items 1, 4, 9, 12, and 13.** No task picks another name, unit, number, or formula.
- **Two modules hold the rules, and neither does I/O.** `modules/location/mounting.py` holds the limits, what counts as a change, and the question. `modules/location/aim.py` holds the road geometry and the percentages. Two repeats are allowed, each tied by a test: the flows check the same limits on what they read from `config.yml`, and the flows and `migrate` read a `^/` command the same way.
- **No arithmetic on these values in the UI** beyond feet to metres and the scaling a drawing needs. Angles, stretches, percentages, the advice, and whether the radar agrees with the file all come from the API.
- **Stored in metres and degrees.** Feet exist only on the page. Speeds stay in the radar's own unit.
- **A `^/` command reaches the radar only from the two typed keys.** Nothing else builds or forwards one.
- **PR 1 changes nothing that is measured.** A unit with the default zeros sends the radar 0 before and after, and a unit with a hand-set angle sends the same angle before and after. Its Pi plan checks both.
- **The serial number stays where it is today.** It is not read into `setup_radar`, the status answer, the setup upload, the control app, a log line, or a fixture.
- **Not private, but not noisy.** The values may appear in an audit row. A config error or a refusal names the key's path, never the value. The engines log nothing.
- **The control app never opens tmdb, and Node-RED never opens `state.sqlite`.**
- **Flows:** edit `flows.json` programmatically and write it back with `json.dumps(flows, indent=4, ensure_ascii=False)` and no trailing newline. New nodes go on the tab and in the group of the nodes they sit beside. No `CREATE` or `ALTER TABLE` in the flows.
- **UI work follows `tm-control/ui/README.md`:** conventional Vuetify, the one dark theme, system fonts, 44 px buttons, results beside the form, no toasts, sentence case, no custom CSS beyond what the README lists. Each UI task's implementer loads the `frontend-design` skill and works test-first; the README's rules win over the skill's taste. New design notes go in the README before the code.
- The API files are regenerated in the same commit as any model change.
- No coordinate in any fixture, commit, PR text, or screenshot other than the docs' example `45.52252, -122.69120` and the fixtures' `45.0, -122.0`.
- Every commit ends with the trailer block from the repo's `CLAUDE.md`; never `Co-Authored-By`. Docs follow "Writing docs" in `docs/development/contributing.md`; `mkdocs build --strict` passes. Nothing public names a device, a bench site, a partner, an outside project, or a private reference.
- **On a dev Pi:** Frigate's detection, snapshots, and recording stay off; an event for the bench is a synthetic `frigate/events` message. A radar's angles are changed only on a bench unit, only with the maintainer's go-ahead for that bench, and are set back to what they were before the check ends, with the radar's answer recorded.

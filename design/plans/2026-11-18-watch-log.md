# Watch Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every five minutes the device records, for each camera and each radar in `config.yml`, whether it was watching, so a reader of the database can tell an empty road from a sensor that was off, and the same rows go to the upload.

**Architecture:** All of it is in the Node-RED flows, one migration, and the upload lists. A new group on the `system` tab subscribes to `frigate/stats`, adds each report up under the camera's key, and on every five-minute mark writes one row per camera to `watch_camera` and one per radar to `watch_radar`. The radar facts are read from `global.tm_status.radars`, which the Status page's nodes already keep. One message per mark carries all the rows to the `thingsboard` tab as a new kind of telemetry, `watch`, and the upload gate keeps only the row fields listed in `upload-lists.json`. The control app doesn't change.

**Tech Stack:** Node-RED 5.0.10 function nodes (JavaScript in `flows.json`), SQLite migrations run by `tmdb_migrate.py`, pytest with the function-node harness in `script/tests/test_node_red_flows.py`, Vue (one example on the Sharing page), MkDocs.

## What it must do

1. **Two tables.** `watch_camera` and `watch_radar` hold one row per sensor per five-minute window. `time` is the five-minute mark that ends the window, in Unix seconds, and `(time, sensor)` is the primary key. Both are `WITHOUT ROWID` tables: the rows are stored in key order with no second copy of the key, which makes them about a quarter smaller.
2. **Which sensors.** Every entry under `sensors.cameras` and `sensors.radars` in `config.yml` gets a row, enabled or not, under its key. A Frigate camera that no entry points at gets none. `enabled` is the entry's `enabled` setting, and `deployment_id` is the sensor's open deployment, empty when it has none.
3. **Cameras.** Node-RED subscribes to `frigate/stats` (Frigate sends one a minute unless its `mqtt.stats_interval` was changed). A camera's row says:
   - `frigate_answered`: 1 when any report arrived in the window, else 0.
   - `stats_messages`: how many of the window's reports listed this camera.
   - `camera_fps`, `process_fps`, `skipped_fps`, `detection_fps`: the mean of those reports' values, to two decimals; empty when there were none.
   - `detection_enabled`: 1 when detection was on in every one of those reports, 0 when it was off in any, empty when there were none.
4. **"Frigate didn't answer" rows.** When no report arrived in a window, every camera still gets its row, with `frigate_answered` 0, `stats_messages` 0, and the five values empty. A window's row never repeats an earlier window's numbers.
5. **Radars.** A radar's row says `port_open` (1 or 0, as at the mark) and `last_reading_at` (Unix seconds, empty when it has sent nothing since Node-RED started), both read from `global.tm_status.radars`. Nothing new is tracked for radars.
6. **Whole windows only.** A row is written only for a window Node-RED saw from one mark to the next (295 to 305 seconds long). The first mark after a start, a mark after a missed one, and a mark after the clock jumped write nothing. No row at all means Node-RED wasn't running for the whole window.
7. **Frigate's camera names stay out.** Reports are filed under the `config.yml` key as they arrive. Frigate's own name for a camera is in no row, no context, no upload, and no log line.
8. **Upload.** Each mark's rows go out as one telemetry message, `values.watch = {cameras: [...], radars: [...]}`, with `ts` the mark in milliseconds. `watch` joins the gate's list of telemetry, and two new lists, `watch_camera` and `watch_radar`, name the row fields that are sent. All of them are sent.
9. **The field rule has a test.** For each table: the rows the flow builds, the INSERT's columns and parameters, the table, and the upload list can't drift apart without a test failing.
10. **The migration only creates the two tables.** Nothing is rewritten.
11. **Docs and the sharing notice** say what is recorded and what is sent, in the same PR.

Not in this change: air quality sensors (their table leaves tmdb with the add-on work); a Status page check or anything else in the control app; a dashboard; the JSON export on the Data export page (the tables reach a reader through the database download); how long rows are kept (as the other tables: until the database is deleted).

def watch_insert(table):
    """The INSERT for a watch table: its node, its columns, and the parameter each one takes."""
    [node] = [node for node in json.loads(FLOWS.read_text())
              if node["type"] == "sqlite" and f"INSERT INTO {table} " in node.get("sql", "")]
    match = re.fullmatch(rf"\s*INSERT INTO {table} \(([^)]*)\)\s*VALUES \((.*)\);\s*", node["sql"], re.DOTALL)
    return node, [name.strip() for name in match[1].split(",")], [value.strip() for value in match[2].split(",")]

## Amendment, 2026-11-19: whether the camera and the radar were on

> **For agentic workers:** Tasks 1 to 8 above are built (branch head `62fb7661` before the plan commits). This section is the whole job for the session that builds it. Read "What it must do", "Global Constraints", "Commands", and "Names used across tasks" above first: they hold except where this section changes them. Use the same sub-skill as the plan.

### Why

On the bench, a camera turned off in Frigate while Frigate kept running wrote rows that look like a working camera. Frigate 0.18.2 keeps a camera that is off in `frigate/stats` and repeats the last frame rates it measured: its watchdog stops ffmpeg and nothing sets the numbers back (`frigate/video/ffmpeg.py`; it does set `camera_fps` to 0 when a stream is down). The rows for a camera that was off said `camera_fps` 10.0, `process_fps` 10.1, `detection_fps` 15.5 for as long as it stayed off. With the camera off and detection left on, `detection_enabled` was 1 as well, so the row passed the docs' "was watching" rule.

The radar's row has the same hole. A radar in idle mode (the API's `PI`: "RF is powered down", no readings) keeps its serial port open, so its row passes the radar's rule, `enabled` and `port_open` both 1. The flows put a radar in idle at the start of every setup and back in active at the end, and their own comments say a command in that run is sometimes lost.

The maintainer's calls, 2026-11-19:

1. The camera's switch is read from Frigate's API, once a minute, not once per window.
2. A camera that was off has no frame rates in its row.
3. The column is `camera_on`. No program's name is in it, so it still fits if another program does the camera's work one day.
4. `enabled`, in both tables, becomes `config_enabled`. It is the setting in `config.yml`, not what the sensor was doing, and beside `camera_on` it read as the live state.
5. The radar is checked the same way: each enabled radar is asked its power state (`P?`) once a minute. `radar_on` is the power state, the radar's own switch, as `camera_on` is the camera's. `radar_answers` counts the answers.
6. The camera's counts are named the same way: `frigate_answered` becomes `frigate_answers`, a count, and `stats_messages` becomes `camera_answers`.
7. `port_open` covers the whole window, as the other 0-or-1 columns do.
8. `last_reading_at` doesn't move for an answer to the minute check.
9. `0004_watch_log.sql` is edited in place.
10. On the bench the maintainer throws Frigate's camera switch.

Differences that stay, and why:

- `last_reading_at` is a time, not a figure for the window. A radar with nothing passing sends little, so it can be older than the window while the radar is working.

### What it must do, added

12. **`camera_on`.** `watch_camera`'s last column: 1 when the camera was on in Frigate in every answer of the window, 0 when it was off in any, empty when the window has no answer about this camera or no `frigate/stats` report at all (`frigate_answers` 0). It has the meaning over a window that `detection_enabled` has.
13. **Where it comes from.** Each time a `frigate/stats` report arrives, Node-RED asks Frigate for its configuration (`GET http://frigate:5000/api/config`) and files each camera's `enabled` value under the camera's `config.yml` key, in the open window. `enabled` there is Frigate's switch as it is now, not the configuration file's value. Nothing is asked when no report arrives, so a stopped Frigate costs no failed request.
14. **No frame rates for a camera that was off.** When `camera_on` is 0, the row's four frame rates are empty. `camera_answers` and `detection_enabled` stay as Frigate reported them. Requirement 4's rule, that a row never repeats an earlier window's numbers, now also holds when it is Frigate that repeats them.
15. **Three names change, and one meaning.** In both tables `enabled` becomes `config_enabled`. In `watch_camera`, `stats_messages` becomes `camera_answers`, and `frigate_answered` becomes `frigate_answers`: how many `frigate/stats` reports arrived in the window, 0 when none, where it was 1 or 0. Nothing outside the watch log is renamed: `config.yml`'s own `enabled` key, `global.tm_status.radars.<name>.enabled`, and the shape of what `GET /tm-internal/status` answers stay.
16. **The radar's minute check.** Once a minute Node-RED sends `P?` to every radar that `config.yml` enables, by the path every other command takes (the radar director). A radar's answer is a line `{"PowerMode" : "<text>"}`. This replaces requirement 5's "nothing new is tracked for radars".
17. **`radar_answers` and `radar_on`.** `watch_radar`'s last two columns. `radar_answers` is how many power state answers the radar gave in the window, 0 when none: about 5, and a few more in a window in which the radar was set up, because `PA` and `PI` print the same line. `radar_on` is 1 when every answer said active, 0 when any said idle, and empty when there was no answer or an answer's text is one this version doesn't know.
18. **The texts.** Read from the bench radar on 2026-11-19: `P?` and `PA` print `{"PowerMode" : "Active Continuously"}`, `PI` and `P?` in idle print `{"PowerMode" : "Idle or Pulse"}`, and `P?` also prints a second line, `{"Power" : "Max"}`. The radar answers while idle. The API note's example for `??` shows `"Continuous"`. So: a text that starts with `Active` or `Continuous`, in any letter case, is active; one that starts with `Idle` is idle; anything else is unknown, and the first one after each config load is warned of once, without quoting it.
19. **`port_open` for the whole window.** 1 only when the port was open at the mark, as before, and at every minute check of the window.
20. **`last_reading_at` is for readings.** The four "last reading" nodes leave out a line that holds `"PowerMode"` or `"Power"`, so the minute check doesn't move the Status page's "last reading" or this column.
21. **Everywhere a column goes.** The INSERTs, the two lists in `upload-lists.json`, the rows in `values.watch`, the Sharing page's example, the docs, the device test, and the tests' constants follow. `test_watch_fields_agree` keeps them together.
22. **The migration is still 0004.** `0004_watch_log.sql` is changed in place: no release and no merged branch has carried it. "Never edit `0001` to `0003`" holds, and from the merge on it holds for `0004` too. A bench unit that already ran 0004 gets the changes by hand (bench item 1).
23. **Requirement 7 holds as written.** Frigate's answer is filed under the `config.yml` key as it arrives. Frigate's name for a camera gains no place.

Not in this change: telling a Frigate whose figures froze for another reason from a working one (the bench saw it once, after its container was paused and resumed; the PR text's limits say so); a switch thrown and thrown back between two checks, under a minute, which is missed; a count of the radar's readings in the window; asking a radar that `config.yml` switches off; any change to the sharing notice, whose sentence already covers the new columns.

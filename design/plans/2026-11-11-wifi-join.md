# Wi-Fi plan 3: joining a Wi-Fi network from the Network page

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On the Network page an admin sees the unit's saved Wi-Fi networks in the order it prefers them and the networks nearby, tests one, reads the result and the address the unit was given, and the unit then joins it after a 5-minute countdown, all without SSH and without ever leaving the unit unreachable. An admin can also forget a saved network and change the order.

**Architecture:**
- tm-control stays unprivileged. It reads the saved profiles with `nmcli` (no secrets asked for) and three root-written files in `/run/traffic-monitor/`: the last scan, the join's state, and the retry's memory of failed networks.
- The short root job `tm-job-network` gains five actions next to `hotspot`: `scan`, `forget`, `order`, `switch-now`, `cancel`.
- A second root job, `tm-job-network-join` (request `/run/tm-control/jobs/network-join.json`), is the long one: scan for the network, test it under a NetworkManager checkpoint, come back, count down, switch. It writes its progress to a state file the page follows, so a restart of tm-control or a phone that rejoins late loses nothing.
- Both jobs and `tm-network-retry` take the one lock plan 2 added. The join job holds it from its first step to its last, countdown included.
- The UI adds a "Wi-Fi networks" section between "This device" and "Hotspot", a Join dialog, a result card, and a banner on the home page.

**Tech Stack:** Python 3 standard library (the root jobs), Python 3.11 + FastAPI + pydantic (tm-control), NetworkManager 1.52 (`nmcli`, and its D-Bus checkpoint calls through `busctl`), `iw`, Ansible (unit, polkit), Vue 3 + Vuetify 3 + TypeScript (Vitest), Material for MkDocs, the dev-Pi tooling (`script/devpi/tmdev.py`). No new Python or npm dependency, no new apt package.

**Spec:** the design summarised in the stub issue, [#294](https://github.com/glossyio/traffic-monitor/issues/294): test, report, then switch, with the checkpoint and the two root jobs that share one state file; the Network page's "Wi-Fi networks" part; which saved network wins, and the backoff of a saved network that won't join; the internet probe in the join test. Its "(maintainer)" items stand; where this plan changes a "(call)", "Decisions" below says so.

**Decided by the maintainer on 2026-11-11, before this was written** (sizes are the code each adds):
1. **The unit scans only when an admin taps Refresh.** A scan needs root and stalls phones on the hotspot for about 2.5 s, so opening the page never starts one. The page shows the last scan with its age. The scan is the `scan` action of `tm-job-network`; it writes `/run/traffic-monitor/network-scan.json`. About 90 lines in the job, 40 in tm-control.
2. **A saved network can be joined without typing its password again.** A saved network that the last scan heard gets Join; the dialog says "Uses the saved password", with a way to type a new one. It runs the same test, report, and countdown. This is also how an operator moves the unit to a network a seller saved for them. About 40 lines in the job, 30 of UI, 60 of tests.
3. **The result shows on the home page too.** On Android the sign-in window closes when the hotspot leaves for the test and reopens on the home page. Admins get one alert there that links to the Network page. About 35 lines of UI.
4. **The password field shows what is typed, in one field**, as the hotspot's does (plan 2, decision 5).
5. **WPA2 and mixed WPA2/WPA3 networks can be joined; a WPA3-only network is listed greyed.** Mixed networks are joined as WPA2. The PR lists WPA3-only under Limits.
6. **While a test or a countdown is under way, every other network change is refused**: a hotspot setting, a scan, Forget, a new order, another Join. tm-control answers 409 with what to do. About 15 lines.
7. **The network being tested lives in memory until the switch** (`nmcli connection add save no`). A password that failed its test, or was cancelled, never reaches the microSD card, and a power cut during the countdown leaves nothing behind. Task 1 B must show that such a profile survives the checkpoint's rollback; if it doesn't, the profile is saved with autoconnect off and deleted on failure and Cancel, as the design has it.
8. **A finished result stays until an admin dismisses it or starts another Join.** Dismiss is the `cancel` action on a finished join. A reboot clears it, because the state file is under `/run`.

**Calls made while writing this plan** (open to change; each is marked where a task depends on it):
9. **Why a test failed comes from the unit's own scan and from exit statuses, never from NetworkManager's sentences.** The design quotes "Secrets were required, but not provided"; the maintainer's rule of 2026-11-05 is that log text is quoted to operators and never the input of a rule, and WPA2 can't tell a wrong password from a refused device anyway. So there are two reasons a test can fail. "Not in range": the join job's own scan didn't hear the network, found before the hotspot is touched. "Couldn't join": `nmcli` failed or timed out; the page says the usual cause is a wrong password and names the MAC address for networks that list their devices. Task 1 D records whether a network that gives no address can be told apart by exit status alone; only then does a third reason get added.
10. **A network that isn't heard is never tested.** The join job scans first (4 s on the bench). The hotspot stays up, the operator's phone stays joined, and the answer arrives on the same page. If the scan itself fails, the test goes ahead.
11. **The checkpoint guards the test, not the switch.** At the switch nothing needs rolling back: when the join fails, the job brings back what the radio was on, and if the job itself dies NetworkManager's own autoconnect picks the hotspot (plan 1's bench, item A). A rollback at the switch would also undo the profile changes the switch has just saved.
12. **The countdown runs on the monotonic clock.** The state file holds the deadline as `time.monotonic()` of the job; tm-control turns it into seconds left. Setting the date on the Time page during a countdown moves nothing. The page counts down from the seconds the unit reports, so the phone's clock doesn't matter either.
13. **The join request is deleted as soon as it is read**, not at the end of the run, so the typed password is on `/run` for a moment and not for five minutes.
14. **A new password for a saved network replaces the saved entry at the switch.** The tested profile is saved, and every other profile with the same network name is deleted, Imager-made (netplan) ones included.
15. **A failed test of a saved network, and a failed join at the end of a countdown, count as failures for the retry.** The join job writes them into `network-retry.json` (it holds the lock), so the waits of 5, 15, and 60 minutes start and the page marks the network "couldn't join". A passed test clears the mark.
16. **The order is rewritten whole.** The `order` action takes every saved network that joins by itself and numbers them from the count down to 1; a newly joined network gets the highest number plus one. Saved networks with autoconnect off are listed under the ordered ones with Forget only. Saved hidden networks are in the order; they can't be told apart from "not in range".
17. **Forget accepts only a Wi-Fi client profile.** Never the hotspot, never Ethernet. When the forgotten network was the one in use and the hotspot starts by itself, the job waits 15 s for NetworkManager to bring up something, then starts the hotspot itself.
18. **One answer for everyone.** Viewers see the saved networks, the last scan, and a pending join, without a control. Nothing in it is a secret.
19. **Rules for the two typed values.** A network name: 1 to 32 bytes of UTF-8, no control characters; spaces at the ends are allowed, because another network's name is what it is. A Wi-Fi password: 8 to 63 printable ASCII characters, spaces included. tm-control also refuses a name that the last scan didn't list as a password network, which is what keeps hidden and typed-in names out.
20. **The internet probe is the job's own two sockets**, both bound to the Wi-Fi device: one DNS question to the Wi-Fi network's own DNS servers, then one `GET` to `connectivity-check.ubuntu.com`, the address the unit already checks every 5 minutes. `204` is "reachable", any other answer is "sign-in page", none is "not reachable". 10 s at most. `curl` can't be told which DNS server to ask on Debian's build. *(Amended after Task 1 H, maintainer 2026-11-11: a DNS question that gets no usable answer is asked once more, still within the 10 s.)*
21. **A radio that is switched off, or isn't built in, is refused with a sentence**, by tm-control and by both jobs. Neither job switches the radio on; turning the hotspot on does that.
22. **The join job exits 0 whenever it reached a result**, a failed test included; it exits 1 only when it was refused or broke. The page follows the state file, not the job: the run outlives `followJob`'s 2 minutes.
23. **IPv4 only**, as on the rest of the page.

## Global Constraints

- The fixed values: device `wlan0` and profile `tm-hotspot` from the manifest; the countdown is 300 s; the checkpoint's rollback timeout is 90 s; a join gets 45 s (`nmcli --wait 45`); the probe gets 10 s; the files are `network-scan.json`, `network-join.json`, `network-join.control`, and `network-retry.json` in `/run/traffic-monitor/`, each 0644 and root's, written under a temporary name and renamed.
- No Wi-Fi password in any log line, job output, audit row, test name, state file, or API answer. The join request is deleted once it is read. Tests and the bench use placeholders, such as `placeholder-pass-1`.
- No test without a checkpoint. If the checkpoint can't be made, the job stops before it touches the radio.
- Nothing here restarts NetworkManager, and the hotspot is never taken away for a network the unit can't hear.
- No change may leave the radio on neither a network nor the hotspot, unless an admin turned the hotspot off after the warning.
- A rule's input is an exit status, a state number, or the unit's own scan. NetworkManager's and `nmcli`'s sentences are never parsed and never quoted (they can carry a command line).
- The root jobs: standard library only, no `tm_control` imports, argv lists (never a shell), a refusal is one sentence with no value from the request in it, and helpers are repeated from the other root scripts rather than imported.
- The words fixed by the design: above the saved list, "The unit joins the first of these it finds."; for a sign-in page network, "Joined, but this network needs a sign-in page, so the unit has no internet there."
- Viewers see the page read-only and never a control.
- UI: conventional Vuetify components, no custom CSS beyond spacing and theme, icons from `@mdi/js`, works offline, logic in the backend. The implementer of Tasks 5 and 10 loads `frontend-design:frontend-design`, `superpowers:test-driven-development`, and `superpowers:verification-before-completion`, adds to the "Network" section of `tm-control/ui/README.md`'s design notes, and screenshots the page in fake mode at phone and desktop width.
- The role: task names `TMSetup - <Component> - <Action>`, `tmsetup_` variables, FQCN modules, `become: true` per task, two-space YAML.
- Docs follow "Writing docs" in `docs/development/contributing.md`; `mkdocs build --strict` passes. Nothing public names a device; later features are "planned" at most.

4. **A network name with a colon, a backslash, a space at the end, an emoji, or bytes `iw` prints as `\xNN`**: read whole from the scan and from `nmcli`, counted in bytes against 32, and passed to `nmcli` as one argument. 5. **An Imager-made network** (a netplan profile): Forget removes it for good, the order sticks, and a new password replaces it. Task 1 E, and Task 12's item on the unit that has one.
6. **A viewer or a logged-out browser calls a changing route**, or a change arrives during a countdown: 403, 401, or 409, and no job starts. Task 4's and Task 8's parametrized tests.
7. **The clock is set during a countdown**: the switch still happens 300 s after the hotspot came back. Task 8's `test_seconds_left_come_from_the_monotonic_clock`.
